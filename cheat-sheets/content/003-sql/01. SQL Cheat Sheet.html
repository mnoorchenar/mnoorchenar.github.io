1. Query Fundamentals

1.1 Anatomy of a Query and Logical Execution Order

SQL queries are written in one order but executed in a different logical order. This matters because it explains what is visible where — for example, why a column alias defined in SELECT cannot be used in WHERE, but can be used in ORDER BY.

Written order Logical execution order
SELECT 1. FROM (and JOINs)
FROM 2. WHERE
WHERE 3. GROUP BY
GROUP BY 4. HAVING
HAVING 5. SELECT (including aliases and window functions)
ORDER BY 6. ORDER BY
LIMIT 7. LIMIT / OFFSET

The practical consequence: WHERE runs before SELECT, so it cannot reference a SELECT alias. HAVING runs after grouping, so it can filter on aggregates. ORDER BY runs last, so it can use SELECT aliases and even column positions.

-- WHERE cannot see the alias 'total', because WHERE runs before SELECT
SELECT price * quantity AS total
FROM orders
WHERE price * quantity > 100; -- must repeat the expression, not "total"

-- ORDER BY can use the alias, since it runs after SELECT
SELECT price * quantity AS total
FROM orders
ORDER BY total DESC;

1.2 SELECT Essentials

Columns and expressions. SELECT can list columns, literal values, arithmetic expressions, function calls, or a mix, each optionally renamed with an alias.

SELECT customer_id, first_name || ' ' || last_name AS full_name, price * 1.1 AS price_with_tax
FROM customers;

Aliases. Column aliases use AS (optional in most dialects, required in Oracle for table aliases in some contexts). Table aliases shorten references in joins and are required for derived tables and self-joins.

SELECT c.customer_id, c.name AS customer_name
FROM customers AS c;

DISTINCT. Removes duplicate rows from the result set, evaluated across all selected columns together, not per column.

SELECT DISTINCT country FROM customers; -- unique countries only
SELECT DISTINCT country, city FROM customers; -- unique combinations, not unique per column

CASE expressions. SQL’s inline conditional logic, usable anywhere an expression is allowed (SELECT, WHERE, ORDER BY, GROUP BY).

SELECT order_id,
       CASE
           WHEN total > 1000 THEN 'large'
           WHEN total > 100 THEN 'medium'
           ELSE 'small'
       END AS order_size
FROM orders;

A shorthand form exists when comparing one expression against several values:

SELECT CASE status WHEN 'A' THEN 'active' WHEN 'I' THEN 'inactive' ELSE 'unknown' END
FROM accounts;

1.3 Sorting and Limiting

ORDER BY sorts the result set. Default direction is ascending (ASC); use DESC for descending. Multiple keys are evaluated left to right.

SELECT name, department, salary
FROM employees
ORDER BY department ASC, salary DESC;

NULL placement in sorting differs by engine: PostgreSQL and Oracle treat NULL as larger than any value by default (NULLs last in ASC order), while MySQL and SQL Server treat NULL as smaller than any value (NULLs first in ASC order). Control it explicitly rather than relying on the default.

SELECT name, commission
FROM employees
ORDER BY commission DESC NULLS LAST; -- PostgreSQL, Oracle syntax

MySQL and SQL Server lack NULLS FIRST/LAST syntax; the common workaround is an ISNULL/COALESCE trick:

SELECT name, commission
FROM employees
ORDER BY CASE WHEN commission IS NULL THEN 1 ELSE 0 END, commission DESC; -- portable equivalent

Limiting rows. Syntax varies significantly by dialect.

Goal PostgreSQL / MySQL / SQLite SQL Server Oracle (12c+)
First N rows LIMIT 10 TOP 10 (in SELECT clause) FETCH FIRST 10 ROWS ONLY
Skip then take LIMIT 10 OFFSET 20 OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY 
-- PostgreSQL / MySQL / SQLite
SELECT * FROM products ORDER BY price DESC LIMIT 10 OFFSET 20;

-- SQL Server
SELECT * FROM products ORDER BY price DESC OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

Pagination pattern. LIMIT/OFFSET is simple but gets slower as OFFSET grows, since the database still scans and discards the skipped rows. For large tables, keyset pagination (also called seek pagination) is faster because it uses an indexed WHERE condition instead of OFFSET.

-- Offset pagination: simple but slow on large offsets
SELECT * FROM orders ORDER BY order_id LIMIT 20 OFFSET 10000;

-- Keyset pagination: fast, uses the last seen id from the previous page
SELECT * FROM orders WHERE order_id > 10000 ORDER BY order_id LIMIT 20;

2. Filtering and Operators

2.1 Comparison and Logical Operators

Comparison operators test equality or ordering between two values.

Operator Meaning
= Equal to
<> or != Not equal to (<> is ANSI standard; both work in most engines)
<, > Less than, greater than
<=, >= Less than or equal, greater than or equal

Logical operators combine or negate conditions. AND has higher precedence than OR, so mixing them without parentheses is a common source of bugs — always parenthesize explicitly when combining AND and OR.

-- Ambiguous to a reader, and easy to get wrong: does NOT bind to just the first condition?
SELECT * FROM orders
WHERE status = 'shipped' OR status = 'pending' AND total > 100;

-- Explicit and unambiguous
SELECT * FROM orders
WHERE status = 'shipped' OR (status = 'pending' AND total > 100);

Operator precedence, from highest to lowest: arithmetic (*, /, +, -), comparison operators, NOT, AND, OR. When in doubt, add parentheses rather than relying on memorized precedence.

2.2 Ranges, Membership, and Pattern Matching

BETWEEN tests an inclusive range on both ends.

SELECT * FROM orders WHERE order_date BETWEEN '2026-01-01' AND '2026-01-31'; -- includes both boundary dates

IN tests membership in a list or subquery, as a readable alternative to a chain of OR conditions.

SELECT * FROM employees WHERE department IN ('sales', 'marketing', 'support');
SELECT * FROM orders WHERE customer_id IN (SELECT customer_id FROM vip_customers);

LIKE / ILIKE do pattern matching using wildcards: % matches any sequence of characters (including none), and _ matches exactly one character. LIKE is case-sensitive in most engines except MySQL (where case sensitivity depends on collation) and SQLite (case-insensitive for ASCII by default). ILIKE is a PostgreSQL-specific case-insensitive variant.

SELECT * FROM products WHERE name LIKE 'Apple%'; -- starts with "Apple"
SELECT * FROM products WHERE name LIKE '%phone%'; -- contains "phone" anywhere
SELECT * FROM products WHERE code LIKE 'A_23'; -- "A" + any one character + "23"
SELECT * FROM products WHERE name ILIKE '%iphone%'; -- PostgreSQL only, case-insensitive

Regular expressions offer more powerful pattern matching but syntax is dialect-specific.

Engine Operator / function
PostgreSQL ~ (match), ~* (case-insensitive match)
MySQL REGEXP or RLIKE
SQL Server no native operator; requires CLR or LIKE workarounds
SQLite REGEXP (requires an extension to be loaded) 
SELECT * FROM users WHERE email ~ '^[a-z]+@[a-z]+\.com$'; -- PostgreSQL
SELECT * FROM users WHERE email REGEXP '^[a-z]+@[a-z]+\\.com$'; -- MySQL

2.3 NULL Logic

NULL represents an unknown or missing value, and it behaves differently from any ordinary value. This is one of the most common sources of SQL bugs.

Three-valued logic. Every condition evaluates to TRUE, FALSE, or UNKNOWN. Any comparison involving NULL — including NULL = NULL — evaluates to UNKNOWN, not TRUE. Rows where a WHERE condition evaluates to UNKNOWN are excluded from the result, exactly as if it were FALSE.

SELECT * FROM employees WHERE commission = NULL; -- always returns zero rows, this is a bug
SELECT * FROM employees WHERE commission IS NULL; -- correct way to test for NULL
SELECT * FROM employees WHERE commission IS NOT NULL; -- correct way to test for non-NULL

Truth table for AND/OR with UNKNOWN:

A B A AND B A OR B
TRUE UNKNOWN UNKNOWN TRUE
FALSE UNKNOWN FALSE UNKNOWN
UNKNOWN UNKNOWN UNKNOWN UNKNOWN

COALESCE returns the first non-NULL value from a list of expressions, commonly used to supply a default.

SELECT name, COALESCE(phone, mobile, 'no contact') AS contact FROM customers; -- falls back through the list

NULLIF returns NULL if two expressions are equal, otherwise returns the first expression — often used to avoid division by zero.

SELECT revenue / NULLIF(units_sold, 0) AS revenue_per_unit FROM sales; -- avoids a divide-by-zero error

NULL and aggregates. Aggregate functions like SUM, AVG, COUNT(column) ignore NULLs rather than treating them as zero; COUNT(*) counts all rows regardless of NULLs. This is covered further in section 4.

3. Joins

3.1 Inner and Outer Joins

Joins combine rows from two or more tables based on a related condition. The four core types differ in which unmatched rows they keep.

Join type Keeps
INNER JOIN Only rows with a match in both tables
LEFT JOIN All rows from the left table, plus matches from the right (NULL where no match)
RIGHT JOIN All rows from the right table, plus matches from the left (NULL where no match)
FULL JOIN All rows from both tables, matched where possible, NULL where not 
-- INNER JOIN: only customers who have placed at least one order
SELECT c.name, o.order_id
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

-- LEFT JOIN: every customer, with NULL order_id if they have no orders
SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- RIGHT JOIN: every order, with NULL name if the customer record is missing
SELECT c.name, o.order_id
FROM customers c
RIGHT JOIN orders o ON c.customer_id = o.customer_id;

-- FULL JOIN: every customer and every order, matched where possible
SELECT c.name, o.order_id
FROM customers c
FULL JOIN orders o ON c.customer_id = o.customer_id;

Note: MySQL does not support FULL JOIN directly. The common workaround is a UNION of a LEFT JOIN and a RIGHT JOIN.

-- MySQL FULL JOIN workaround
SELECT c.name, o.order_id FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id
UNION
SELECT c.name, o.order_id FROM customers c RIGHT JOIN orders o ON c.customer_id = o.customer_id;

RIGHT JOIN is rarely used in practice since any RIGHT JOIN can be rewritten as a LEFT JOIN by swapping the table order; many style guides prefer LEFT JOIN exclusively for consistency.

3.2 Special Join Patterns

CROSS JOIN produces the Cartesian product: every row from the first table paired with every row from the second. Useful for generating combinations, dangerous by accident (it multiplies row counts fast).

SELECT s.size, c.color FROM sizes s CROSS JOIN colors c; -- every size/color combination

Self joins join a table to itself, typically to compare rows within the same table, such as employees to their managers. Table aliases are required to distinguish the two references.

SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.employee_id;

Semi joins and anti joins filter rows in one table based on existence (or non-existence) of a match in another, without actually pulling columns from the second table. SQL has no dedicated SEMI JOIN or ANTI JOIN keyword; these are expressed with EXISTS / NOT EXISTS or IN / NOT IN.

-- Semi join: customers who have placed at least one order (no order columns returned)
SELECT c.name FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

-- Anti join: customers who have never placed an order
SELECT c.name FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

USING vs ON. ON allows any join condition and differing column names. USING is shorthand for equi-joins on identically named columns, and it also collapses the duplicate column in the output.

SELECT * FROM orders o JOIN customers c ON o.customer_id = c.customer_id; -- customer_id appears twice
SELECT * FROM orders JOIN customers USING (customer_id); -- customer_id appears once

NATURAL JOIN automatically joins on all columns sharing the same name in both tables. It is concise but risky: adding a new shared column name later silently changes the join behavior, so most style guides discourage it in production code.

SELECT * FROM orders NATURAL JOIN customers; -- joins on every identically named column

LATERAL joins (PostgreSQL) / CROSS APPLY (SQL Server) allow a subquery on the right side to reference columns from tables on the left side of the join — something an ordinary join cannot do. Commonly used for “top N per group” queries.

-- PostgreSQL: latest 3 orders per customer
SELECT c.name, o.order_id, o.order_date
FROM customers c
CROSS JOIN LATERAL (
    SELECT order_id, order_date FROM orders o WHERE o.customer_id = c.customer_id
    ORDER BY order_date DESC LIMIT 3
) o;

-- SQL Server equivalent
SELECT c.name, o.order_id, o.order_date
FROM customers c
CROSS APPLY (
    SELECT TOP 3 order_id, order_date FROM orders o WHERE o.customer_id = c.customer_id
    ORDER BY order_date DESC
) o;

3.3 Join Pitfalls

Row multiplication. When the join key is not unique on one or both sides, the result can contain far more rows than either input table. This is the single most common cause of inflated aggregate totals after a join.

-- If a customer has 3 orders and each order has 4 line items, this join produces 12 rows for that customer,
-- and a naive SUM(order.total) grouped by customer will overcount by a factor of 4.
SELECT c.customer_id, o.total, li.line_item_id
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
JOIN line_items li ON o.order_id = li.order_id;

Filtering in ON vs WHERE for outer joins. This is a classic gotcha. Putting a filter on the right-hand table in the ON clause preserves the outer join’s behavior; putting it in WHERE effectively turns the outer join into an inner join, because unmatched rows have NULL and fail the WHERE condition.

-- Correct: keeps all customers, only showing shipped orders where they exist
SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'shipped';

-- Incorrect: silently becomes an inner join, dropping customers with no shipped order
SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'shipped';

Duplicate handling. After a join that multiplies rows, DISTINCT or pre-aggregation (aggregating one side before joining) are the two common fixes, and pre-aggregation is usually the more correct and efficient choice.

-- Pre-aggregate orders before joining, avoiding row multiplication entirely
SELECT c.customer_id, o.order_count
FROM customers c
JOIN (SELECT customer_id, COUNT(*) AS order_count FROM orders GROUP BY customer_id) o
ON c.customer_id = o.customer_id;

4. Aggregation and Grouping

4.1 Aggregate Functions

Aggregate functions collapse multiple rows into a single summary value.

Function Purpose
COUNT(*) Number of rows, regardless of NULLs
COUNT(column) Number of non-NULL values in that column
COUNT(DISTINCT column) Number of distinct non-NULL values
SUM(column) Total of non-NULL values
AVG(column) Average of non-NULL values
MIN(column) / MAX(column) Smallest / largest value, NULLs ignored 
SELECT COUNT(*) AS total_rows, COUNT(discount) AS rows_with_discount, COUNT(DISTINCT customer_id) AS unique_customers,
       SUM(total) AS revenue, AVG(total) AS avg_order_value, MAX(order_date) AS most_recent_order
FROM orders;

COUNT(*) vs COUNT(column) is a frequent source of confusion: if a column has NULLs, COUNT(column) will return a smaller number than COUNT(*), since NULLs are simply skipped.

DISTINCT inside aggregates counts or aggregates only unique values.

SELECT COUNT(DISTINCT product_id) AS unique_products_sold FROM order_items;

String aggregation concatenates grouped text values into one string. Syntax varies sharply across engines.

Engine Function
PostgreSQL STRING_AGG(column, separator)
MySQL GROUP_CONCAT(column SEPARATOR separator)
SQL Server STRING_AGG(column, separator) (2017+)
SQLite GROUP_CONCAT(column, separator) 
-- PostgreSQL / SQL Server 2017+
SELECT customer_id, STRING_AGG(product_name, ', ') AS products
FROM order_items GROUP BY customer_id;

-- MySQL
SELECT customer_id, GROUP_CONCAT(product_name SEPARATOR ', ') AS products
FROM order_items GROUP BY customer_id;

4.2 GROUP BY and HAVING

GROUP BY partitions rows into groups sharing the same values in the specified columns, and aggregate functions then compute one result per group. Every column in SELECT that is not itself aggregated must appear in GROUP BY (strictly enforced in PostgreSQL and SQL Server; MySQL allows exceptions by default, which can produce nondeterministic results).

SELECT department, COUNT(*) AS headcount, AVG(salary) AS avg_salary
FROM employees
GROUP BY department;

WHERE vs HAVING. WHERE filters individual rows before grouping happens; HAVING filters entire groups after aggregation. A condition on an aggregate function must go in HAVING, because the aggregate does not exist yet at the point WHERE is evaluated.

-- WHERE filters rows first (only active employees are considered)
-- HAVING filters groups after aggregation (only departments with more than 5 people)
SELECT department, COUNT(*) AS headcount
FROM employees
WHERE status = 'active'
GROUP BY department
HAVING COUNT(*) > 5;
-- Common mistake: aggregate function in WHERE, this is invalid SQL
SELECT department, COUNT(*)
FROM employees
WHERE COUNT(*) > 5 -- error: aggregate functions are not allowed in WHERE
GROUP BY department;

4.3 Advanced Grouping

ROLLUP produces subtotal rows for a hierarchy of groupings, plus a grand total, in a single query.

-- Produces: subtotal per (region, product), subtotal per region, and one grand total row
SELECT region, product, SUM(sales) AS total_sales
FROM sales_data
GROUP BY ROLLUP (region, product);

CUBE produces subtotals for every possible combination of the grouped columns, not just a hierarchy.

-- Produces: (region, product), (region, all products), (all regions, product), and grand total
SELECT region, product, SUM(sales) AS total_sales
FROM sales_data
GROUP BY CUBE (region, product);

GROUPING SETS lets you specify exactly which combinations of groupings you want, when ROLLUP or CUBE would produce more than needed.

SELECT region, product, SUM(sales) AS total_sales
FROM sales_data
GROUP BY GROUPING SETS ((region, product), (region), ());

MySQL supports ROLLUP (as WITH ROLLUP appended after GROUP BY) but not CUBE or GROUPING SETS directly.

Conditional aggregation and pivoting with CASE/FILTER. Turning row values into columns (“pivoting”) without a dedicated PIVOT keyword — standard SQL does this by wrapping aggregates in CASE expressions.

-- Pivot order counts by status into columns, portable across all major engines
SELECT customer_id,
       COUNT(CASE WHEN status = 'shipped' THEN 1 END) AS shipped_count,
       COUNT(CASE WHEN status = 'cancelled' THEN 1 END) AS cancelled_count
FROM orders
GROUP BY customer_id;

PostgreSQL offers a cleaner syntax for the same pattern using the FILTER clause.

-- PostgreSQL-only shorthand, equivalent to the CASE version above
SELECT customer_id,
       COUNT(*) FILTER (WHERE status = 'shipped') AS shipped_count,
       COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled_count
FROM orders
GROUP BY customer_id;

5. Subqueries, CTEs, and Set Operations

5.1 Subqueries

A subquery is a query nested inside another query. It can return a single value (scalar), a single row of multiple columns, or a full table of rows, and each shape is usable only in certain contexts.

Scalar subqueries return exactly one row and one column, and can be used anywhere a single value is expected.

SELECT name, salary, (SELECT AVG(salary) FROM employees) AS company_avg
FROM employees;

Row subqueries return a single row with multiple columns, comparable against a row constructor.

SELECT * FROM orders
WHERE (customer_id, order_date) = (SELECT customer_id, MAX(order_date) FROM orders WHERE customer_id = 42);

Table subqueries return multiple rows and columns, used in FROM (as a derived table) or with IN/EXISTS.

SELECT department, avg_salary
FROM (SELECT department, AVG(salary) AS avg_salary FROM employees GROUP BY department) AS dept_avg
WHERE avg_salary > 60000;

Correlated subqueries reference a column from the outer query, so they are re-evaluated once per outer row rather than once overall. This makes them powerful but potentially slow on large tables, since a naive engine may execute the subquery row by row.

-- For each employee, find whether their salary is above their own department's average
SELECT e.name, e.salary, e.department
FROM employees e
WHERE e.salary > (SELECT AVG(e2.salary) FROM employees e2 WHERE e2.department = e.department);

EXISTS vs IN vs JOIN. All three can express “rows that have a match elsewhere,” but they behave differently, especially with NULLs and duplicates.

Approach Behavior
JOIN Returns columns from both tables; duplicates rows if the match is not unique
IN (subquery) Simple membership test; can behave unexpectedly if the subquery result contains NULL
EXISTS (subquery) Tests only for presence of a matching row; stops at the first match, unaffected by NULLs in the subquery 
-- IN: dangerous if the subquery can return NULL, since "x NOT IN (list containing NULL)" is always UNKNOWN
SELECT * FROM customers WHERE customer_id IN (SELECT customer_id FROM orders);

-- EXISTS: safer and often faster, unaffected by NULLs in the subquery
SELECT * FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

The NOT IN with NULL pitfall deserves special attention, and is covered again in section 10.3.

5.2 Common Table Expressions

WITH syntax. A CTE names a subquery so it can be referenced later in the same statement, improving readability over deeply nested subqueries.

WITH high_value_orders AS (
    SELECT customer_id, total FROM orders WHERE total > 1000
)
SELECT c.name, h.total
FROM customers c
JOIN high_value_orders h ON c.customer_id = h.customer_id;

Chaining CTEs. Multiple CTEs can be defined in one WITH clause, each able to reference the ones defined before it.

WITH regional_sales AS (
    SELECT region, SUM(sales) AS total_sales FROM sales_data GROUP BY region
),
top_regions AS (
    SELECT region FROM regional_sales WHERE total_sales > 100000
)
SELECT * FROM sales_data WHERE region IN (SELECT region FROM top_regions);

Recursive CTEs. Used for hierarchical data (org charts, category trees) or generating sequences. They consist of an anchor member (base case) and a recursive member (repeated step) joined by UNION ALL.

-- Hierarchy: find all employees under a given manager, at any depth
WITH RECURSIVE org_chart AS (
    SELECT employee_id, manager_id, name, 1 AS depth
    FROM employees
    WHERE employee_id = 1 -- anchor: the starting manager
    UNION ALL
    SELECT e.employee_id, e.manager_id, e.name, oc.depth + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.employee_id -- recursive step
)
SELECT * FROM org_chart;
-- Generating a series: all dates in January 2026
WITH RECURSIVE date_series AS (
    SELECT DATE '2026-01-01' AS d
    UNION ALL
    SELECT d + 1 FROM date_series WHERE d < DATE '2026-01-31'
)
SELECT * FROM date_series;

Note: MySQL requires WITH RECURSIVE (same as PostgreSQL); SQL Server uses plain WITH without the RECURSIVE keyword but the same anchor/recursive structure; SQLite supports WITH RECURSIVE as well. Many engines also offer a dedicated series generator as a simpler alternative, such as PostgreSQL’s generate_series().

5.3 Set Operations

Set operations combine the results of two or more SELECT statements. All participating queries must have the same number of columns, with compatible data types in corresponding positions.

Operation Result
UNION Rows from both queries, duplicates removed
UNION ALL Rows from both queries, duplicates kept
INTERSECT Only rows present in both queries
EXCEPT (or MINUS in Oracle) Rows in the first query but not the second 
-- UNION ALL is preferred over UNION when duplicates are not a concern, since UNION forces a deduplication pass
SELECT customer_id FROM online_orders
UNION ALL
SELECT customer_id FROM store_orders;

-- INTERSECT: customers who ordered both online and in-store
SELECT customer_id FROM online_orders
INTERSECT
SELECT customer_id FROM store_orders;

-- EXCEPT: customers who ordered online but never in-store
SELECT customer_id FROM online_orders
EXCEPT
SELECT customer_id FROM store_orders;

MySQL added native INTERSECT and EXCEPT support only in version 8.0.31+; earlier versions require workarounds using JOIN or NOT IN/EXISTS. Oracle uses the keyword MINUS instead of EXCEPT.

Column compatibility rules. The column names in the final result come from the first query only; later queries’ column names are ignored. Column order matters — types are matched positionally, not by name.

-- Result columns are named "id" and "label", taken from the first SELECT, even though the second uses different names
SELECT customer_id AS id, name AS label FROM customers
UNION
SELECT product_id, product_name FROM products;

6. Window Functions

6.1 Window Syntax

Window functions perform calculations across a set of rows related to the current row, without collapsing those rows into a single output row the way GROUP BY does. Every row keeps its identity, and the calculation appears as an additional column.

OVER, PARTITION BY, ORDER BY. The OVER clause defines the window. PARTITION BY divides rows into groups, similar to GROUP BY, but each row is still returned individually. ORDER BY within OVER defines the sequence used for ranking, running totals, and offset functions.

SELECT employee_id, department, salary,
       AVG(salary) OVER (PARTITION BY department) AS dept_avg_salary
FROM employees;

Every employee row is still returned, but each now carries its department’s average alongside it — something GROUP BY alone cannot do without a separate join back to the original rows.

How windows differ from GROUP BY.

Aspect GROUP BY Window function
Row count in output One row per group One row per input row
Access to non-aggregated columns Only grouped columns All original columns remain
Can combine multiple granularities Requires separate queries or joins Yes, in a single SELECT 
-- Compare each employee's salary to the department average, in one query, no join or subquery needed
SELECT employee_id, department, salary,
       salary - AVG(salary) OVER (PARTITION BY department) AS diff_from_dept_avg
FROM employees;

6.2 Ranking and Offset Functions

Ranking functions assign a position to each row within its partition, based on the ORDER BY inside OVER.

Function Behavior on ties
ROW_NUMBER() Assigns a unique, arbitrary sequential number even to tied rows
RANK() Tied rows get the same rank; the next rank skips ahead (1, 1, 3)
DENSE_RANK() Tied rows get the same rank; the next rank does not skip (1, 1, 2)
NTILE(n) Divides rows into n roughly equal buckets 
SELECT employee_id, department, salary,
       ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS row_num,
       RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rank,
       DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dense_rank
FROM employees;

Offset functions look at values from other rows relative to the current one, within the same ordered window.

Function Purpose
LAG(column, n) Value from n rows before the current row
LEAD(column, n) Value from n rows after the current row
FIRST_VALUE(column) First value in the window frame
LAST_VALUE(column) Last value in the window frame (frame-sensitive, see 6.3) 
-- Compare each month's revenue to the previous and next month
SELECT month, revenue,
       LAG(revenue, 1) OVER (ORDER BY month) AS prev_month_revenue,
       LEAD(revenue, 1) OVER (ORDER BY month) AS next_month_revenue
FROM monthly_sales;

6.3 Frames and Common Patterns

ROWS vs RANGE. The frame clause narrows the window further, to a subset of rows around the current one. ROWS counts physical rows; RANGE groups by logical value, treating rows with equal ORDER BY values as a single peer group. This distinction matters most when there are ties in the ORDER BY column.

-- ROWS: exactly the 2 preceding physical rows plus the current row
SELECT order_date, revenue,
       SUM(revenue) OVER (ORDER BY order_date ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS rolling_3day_total
FROM daily_sales;

Default frame behavior differs by presence of ORDER BY: with ORDER BY and no explicit frame, most engines default to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. This default is why LAST_VALUE often surprisingly returns the current row’s value rather than the true last row — the frame stops at the current row unless widened explicitly.

-- Common gotcha: LAST_VALUE with the default frame returns the current row, not the actual last row
SELECT order_date, revenue,
       LAST_VALUE(revenue) OVER (ORDER BY order_date) AS wrong_last_value, -- returns current row's value
       LAST_VALUE(revenue) OVER (ORDER BY order_date
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS correct_last_value
FROM daily_sales;

Running totals.

SELECT order_date, revenue,
       SUM(revenue) OVER (ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM daily_sales;

Moving averages.

SELECT order_date, revenue,
       AVG(revenue) OVER (ORDER BY order_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS moving_avg_7day
FROM daily_sales;

Top-N per group. A very common use of ROW_NUMBER: filtering to the top N rows within each partition. Note that window functions cannot be used directly in WHERE, since WHERE executes before window functions in logical order, so this pattern requires a CTE or subquery.

WITH ranked_orders AS (
    SELECT customer_id, order_id, total,
           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total DESC) AS rn
    FROM orders
)
SELECT * FROM ranked_orders WHERE rn <= 3; -- top 3 orders per customer

Deduplication. The same ROW_NUMBER pattern removes duplicate rows, keeping one representative row per key based on a chosen tiebreaker.

WITH deduped AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at DESC) AS rn
    FROM users
)
SELECT * FROM deduped WHERE rn = 1; -- keeps only the most recently created row per email

MySQL and SQLite support window functions since MySQL 8.0 and SQLite 3.25, respectively; earlier versions require workarounds using self-joins or variables.

7. Data Modification and Transactions

7.1 INSERT, UPDATE, DELETE

Multi-row inserts add several rows in a single statement, more efficient than one INSERT per row.

INSERT INTO products (name, price, category)
VALUES ('Widget', 9.99, 'tools'), ('Gadget', 19.99, 'electronics'), ('Gizmo', 14.99, 'tools');

INSERT…SELECT copies rows from a query result directly into a table, without needing to pull data out and back in.

INSERT INTO archived_orders (order_id, customer_id, total, order_date)
SELECT order_id, customer_id, total, order_date FROM orders WHERE order_date < '2020-01-01';

UPDATE and DELETE with joins. Standard SQL restricts UPDATE and DELETE to a single table, but most engines allow referencing other tables to determine which rows to affect, with differing syntax.

-- PostgreSQL: UPDATE ... FROM
UPDATE orders o
SET status = 'flagged'
FROM customers c
WHERE o.customer_id = c.customer_id AND c.is_fraud_suspect = TRUE;

-- MySQL: multi-table UPDATE with JOIN
UPDATE orders o
JOIN customers c ON o.customer_id = c.customer_id
SET o.status = 'flagged'
WHERE c.is_fraud_suspect = TRUE;

-- SQL Server: UPDATE ... FROM ... JOIN
UPDATE o
SET o.status = 'flagged'
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE c.is_fraud_suspect = TRUE;
-- DELETE using a subquery, portable across all major engines
DELETE FROM orders
WHERE customer_id IN (SELECT customer_id FROM customers WHERE is_fraud_suspect = TRUE);

TRUNCATE vs DELETE. Both remove rows, but they behave very differently.

Aspect DELETE TRUNCATE
WHERE clause Supported, can remove a subset Not supported, always removes all rows
Speed Slower, logs each row removal Much faster, deallocates pages
Triggers Fires row-level triggers Usually does not fire row-level triggers
Rollback Fully transactional in all major engines Transactional in PostgreSQL and SQL Server; auto-commits in MySQL (InnoDB)
Identity/auto-increment reset Preserved Typically reset to its starting value 
DELETE FROM logs WHERE created_at < '2025-01-01'; -- removes only old rows
TRUNCATE TABLE temp_staging; -- removes everything, fast, resets identity

7.2 Upserts and Returning Data

Upserts insert a row, or update it instead if a conflicting key already exists. Syntax is heavily dialect-specific.

-- PostgreSQL / SQLite: ON CONFLICT
INSERT INTO inventory (product_id, quantity)
VALUES (101, 50)
ON CONFLICT (product_id) DO UPDATE SET quantity = inventory.quantity + EXCLUDED.quantity;

-- MySQL: ON DUPLICATE KEY UPDATE
INSERT INTO inventory (product_id, quantity)
VALUES (101, 50)
ON DUPLICATE KEY UPDATE quantity = quantity + VALUES(quantity);

MERGE is the ANSI-standard statement for combining insert, update, and delete logic based on a match condition, available in SQL Server, Oracle, and PostgreSQL (15+).

MERGE INTO inventory AS target
USING (SELECT 101 AS product_id, 50 AS quantity) AS source
ON target.product_id = source.product_id
WHEN MATCHED THEN UPDATE SET target.quantity = target.quantity + source.quantity
WHEN NOT MATCHED THEN INSERT (product_id, quantity) VALUES (source.product_id, source.quantity);

RETURNING / OUTPUT. Retrieves values from the affected rows immediately, without a separate SELECT. Useful for getting a generated ID right after an insert.

-- PostgreSQL / SQLite: RETURNING
INSERT INTO customers (name, email) VALUES ('Ana Silva', 'ana@example.com') RETURNING customer_id;

-- SQL Server: OUTPUT
INSERT INTO customers (name, email) OUTPUT inserted.customer_id VALUES ('Ana Silva', 'ana@example.com');

MySQL has no equivalent to RETURNING/OUTPUT for INSERT; the common approach is a separate call to retrieve the last generated ID, such as LAST_INSERT_ID().

7.3 Transactions

BEGIN/COMMIT/ROLLBACK. A transaction groups multiple statements so they succeed or fail as a unit. COMMIT makes changes permanent; ROLLBACK undoes everything since the transaction began.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT; -- both updates become permanent together, or neither does

MySQL and SQL Server use START TRANSACTION or BEGIN TRANSACTION respectively; PostgreSQL and SQLite use BEGIN. Most engines auto-commit each statement by default unless a transaction is explicitly started.

Savepoints mark a point within a transaction that can be rolled back to, without discarding the entire transaction.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
SAVEPOINT before_bonus;
UPDATE accounts SET balance = balance + 10 WHERE account_id = 1; -- a bonus that turns out to be wrong
ROLLBACK TO SAVEPOINT before_bonus; -- undoes just the bonus update, keeps the first one
COMMIT;

ACID describes the guarantees a transaction should provide.

Property Meaning
Atomicity All statements in the transaction succeed, or none do
Consistency The database moves from one valid state to another, respecting constraints
Isolation Concurrent transactions do not see each other’s uncommitted changes
Durability Once committed, changes survive even a system crash

Isolation levels and anomalies. Isolation is tunable, trading consistency guarantees for performance. Lower levels allow more concurrency but risk seeing inconsistent data.

Isolation level Dirty read Non-repeatable read Phantom read
Read Uncommitted Possible Possible Possible
Read Committed Prevented Possible Possible
Repeatable Read Prevented Prevented Possible
Serializable Prevented Prevented Prevented
  • Dirty read: reading a row that another transaction has changed but not yet committed.
  • Non-repeatable read: re-reading the same row within a transaction and getting a different value because another transaction committed a change in between.
  • Phantom read: re-running the same query and getting different rows because another transaction inserted or deleted matching rows in between.
-- PostgreSQL / SQL Server / MySQL
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

PostgreSQL defaults to Read Committed; MySQL (InnoDB) defaults to Repeatable Read; SQL Server defaults to Read Committed. SQLite is fully serializable by default due to its locking model.

8. Schema Definition and Views

8.1 Creating Tables and Data Types

CREATE TABLE defines a new table’s columns, types, and constraints.

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    hire_date DATE NOT NULL,
    salary NUMERIC(10, 2),
    department_id INT
);

Core data types by category. Names and available precision vary by engine, but the categories map fairly consistently.

Category PostgreSQL MySQL SQL Server SQLite
Integer INTEGER, BIGINT, SMALLINT INT, BIGINT, SMALLINT INT, BIGINT, SMALLINT INTEGER (dynamic typing)
Exact decimal NUMERIC(p, s) DECIMAL(p, s) DECIMAL(p, s) NUMERIC (stored flexibly)
Floating point REAL, DOUBLE PRECISION FLOAT, DOUBLE REAL, FLOAT REAL
Variable text VARCHAR(n), TEXT VARCHAR(n), TEXT VARCHAR(n), NVARCHAR(n) TEXT
Date/time DATE, TIMESTAMP, TIMESTAMPTZ DATE, DATETIME, TIMESTAMP DATE, DATETIME2 TEXT or NUMERIC (no native type)
Boolean BOOLEAN TINYINT(1) (no true boolean) BIT INTEGER (0 or 1)
JSON JSON, JSONB JSON NVARCHAR + JSON functions TEXT + JSON1 extension

Use NUMERIC/DECIMAL rather than floating-point types for money and other values where exact precision matters, since floating-point types can introduce rounding errors.

Identity / auto-increment columns generate sequential values automatically, commonly used for primary keys.

-- PostgreSQL (modern, SQL-standard syntax)
CREATE TABLE orders (order_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, ...);

-- MySQL
CREATE TABLE orders (order_id INT AUTO_INCREMENT PRIMARY KEY, ...);

-- SQL Server
CREATE TABLE orders (order_id INT IDENTITY(1,1) PRIMARY KEY, ...);

-- SQLite
CREATE TABLE orders (order_id INTEGER PRIMARY KEY AUTOINCREMENT, ...); -- plain INTEGER PRIMARY KEY already auto-increments

8.2 Constraints and Keys

PRIMARY KEY uniquely identifies each row; a table can have only one, though it may span multiple columns (a composite key).

CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    PRIMARY KEY (order_id, product_id) -- composite primary key
);

FOREIGN KEY enforces that a column’s values must exist in another table’s referenced column, maintaining referential integrity. ON DELETE/ON UPDATE actions control what happens to dependent rows when the referenced row changes.

Action Effect
CASCADE Automatically apply the same delete/update to dependent rows
SET NULL Set the foreign key column to NULL
RESTRICT / NO ACTION Reject the operation if dependent rows exist
SET DEFAULT Set the foreign key column to its default value 
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE CASCADE ON UPDATE RESTRICT
);

UNIQUE ensures all values in a column (or set of columns) are distinct, allowing multiple NULLs in most engines (since NULL is not considered equal to another NULL).

CREATE TABLE users (email VARCHAR(255) UNIQUE, ...);

CHECK enforces an arbitrary boolean condition on column values.

CREATE TABLE products (price NUMERIC(10, 2) CHECK (price > 0), ...);

Note: MySQL silently ignored CHECK constraints before version 8.0.16; verify engine version if relying on this.

NOT NULL requires a value to be present. DEFAULT supplies a value automatically when none is given.

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    status VARCHAR(20) NOT NULL DEFAULT 'pending',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

8.3 Altering Schema and Views

ALTER / DROP. ALTER TABLE modifies an existing table’s structure; DROP TABLE removes it entirely.

ALTER TABLE employees ADD COLUMN phone VARCHAR(20);
ALTER TABLE employees DROP COLUMN phone;
ALTER TABLE employees ALTER COLUMN salary TYPE NUMERIC(12, 2); -- PostgreSQL syntax
ALTER TABLE employees MODIFY COLUMN salary DECIMAL(12, 2); -- MySQL syntax
DROP TABLE employees; -- fails if other tables reference it via foreign key, unless CASCADE is used
DROP TABLE employees CASCADE; -- also drops dependent objects, use with caution

Renaming objects also varies by engine.

-- PostgreSQL
ALTER TABLE employees RENAME TO staff;
ALTER TABLE staff RENAME COLUMN phone TO phone_number;

-- MySQL
RENAME TABLE employees TO staff;
ALTER TABLE staff CHANGE phone phone_number VARCHAR(20);

-- SQL Server
EXEC sp_rename 'employees', 'staff';

Views are stored queries that behave like virtual tables, useful for encapsulating complex logic or restricting access to specific columns/rows.

CREATE VIEW active_customers AS
SELECT customer_id, name, email FROM customers WHERE status = 'active';

SELECT * FROM active_customers WHERE name LIKE 'A%'; -- queries the view like any table

Updatable views. A view is updatable (supports INSERT/UPDATE/DELETE through it) only if it meets certain conditions: it must be based on a single table, contain no aggregates, GROUP BY, DISTINCT, or set operations, and select all NOT NULL columns without a default. Views violating these rules are read-only unless the engine provides special support (such as PostgreSQL’s INSTEAD OF triggers).

UPDATE active_customers SET email = 'new@example.com' WHERE customer_id = 5; -- works if the view is simple enough

Materialized views store the query’s result physically on disk, rather than recomputing it on every access. This trades freshness for speed, and requires manual or scheduled refreshing.

-- PostgreSQL / Oracle
CREATE MATERIALIZED VIEW sales_summary AS
SELECT region, SUM(sales) AS total_sales FROM sales_data GROUP BY region;

REFRESH MATERIALIZED VIEW sales_summary; -- must be run explicitly to pick up new data

MySQL has no native materialized view; common workarounds are a regular table refreshed by a scheduled event, or a manually managed summary table.

9. Indexes and Query Performance

9.1 Index Fundamentals

An index is a separate data structure that lets the database find rows without scanning the entire table, at the cost of extra storage and slower writes (since the index must be updated on every insert, update, or delete).

Index types.

Type Best for Notes
B-tree Range queries, equality, sorting (<, >, BETWEEN, ORDER BY) The default index type in nearly every engine
Hash Pure equality lookups (=) only Cannot support range queries or sorting
Bitmap Low-cardinality columns (few distinct values), common in data warehouses Native mainly in Oracle; PostgreSQL builds bitmaps dynamically at query time
GIN / GiST (PostgreSQL) Full-text search, arrays, JSONB, geometric data Specialized, not general-purpose 
CREATE INDEX idx_orders_customer_id ON orders (customer_id); -- B-tree by default in most engines
CREATE INDEX idx_orders_status_hash ON orders USING HASH (status); -- PostgreSQL hash index syntax

Composite index column order matters: a multi-column index is only efficiently searchable using its leftmost columns first, similar to how a phone book sorted by (last name, first name) is not useful for looking someone up by first name alone.

CREATE INDEX idx_orders_customer_date ON orders (customer_id, order_date);

-- Uses the index efficiently: filters on the leftmost column, or both columns together
SELECT * FROM orders WHERE customer_id = 42;
SELECT * FROM orders WHERE customer_id = 42 AND order_date > '2026-01-01';

-- Cannot use this index efficiently: skips the leftmost column
SELECT * FROM orders WHERE order_date > '2026-01-01';

Covering indexes include all the columns a query needs, letting the engine answer the query directly from the index without touching the table itself (an “index-only scan”).

-- PostgreSQL: INCLUDE adds columns to the index for coverage without making them part of the search key
CREATE INDEX idx_orders_covering ON orders (customer_id) INCLUDE (order_date, total);

Partial indexes cover only a subset of rows matching a condition, useful when queries consistently filter on a specific value and the full-table index would be wasteful.

-- PostgreSQL: only indexes pending orders, much smaller than a full index if most orders are not pending
CREATE INDEX idx_pending_orders ON orders (order_date) WHERE status = 'pending';

MySQL does not support partial indexes; SQL Server offers an equivalent called a filtered index with similar syntax (CREATE INDEX ... WHERE ...).

9.2 Reading Execution Plans

EXPLAIN / EXPLAIN ANALYZE shows how the database engine intends to execute a query (or, with ANALYZE, actually executes it and reports real timing and row counts).

EXPLAIN SELECT * FROM orders WHERE customer_id = 42; -- shows the planned execution strategy
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42; -- actually runs the query and reports real stats

SQL Server uses SET STATISTICS IO, TIME ON alongside execution plans, or the graphical “Show Execution Plan” in SQL Server Management Studio, rather than an ANALYZE keyword.

Scan types. The plan reveals how each table is accessed.

Scan type Meaning
Sequential / table scan Reads every row in the table; fine for small tables, expensive for large ones
Index scan Reads through an index in order, then fetches matching rows
Index-only scan Answers the query entirely from the index, no table access needed
Index seek Jumps directly to matching rows using the index, without scanning it

A sequential scan on a large table where an index scan or seek was expected is usually a sign of a missing index, an unusable index (see 9.3), or the optimizer deciding a scan is cheaper (common when the query needs a large fraction of the table anyway).

Join algorithms. The plan also shows how the engine physically executes each join.

Algorithm Best when
Nested loop One side is small, or a good index exists on the join key
Hash join Both sides are large and unsorted, no useful index on the join key
Merge join Both sides are already sorted on the join key (often because of an index)

9.3 Writing Fast Queries

Sargability (“Search ARGument ABLE”) describes whether a condition can actually use an index. A condition is sargable if it compares a column directly to a value or expression, without wrapping the column itself in a function or transformation.

-- Not sargable: wrapping the indexed column in a function prevents the index from being used
SELECT * FROM orders WHERE YEAR(order_date) = 2026;

-- Sargable: an equivalent range condition, can use an index on order_date
SELECT * FROM orders WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01';

Functions on indexed columns. The same principle applies broadly: any function applied to a column in a WHERE clause typically disables index use for that column, unless a matching functional/expression index is created.

-- Not sargable
SELECT * FROM users WHERE LOWER(email) = 'ana@example.com';

-- Option 1: rewrite to avoid the function on the column, if possible
SELECT * FROM users WHERE email = 'ana@example.com'; -- relies on consistent casing at insert time

-- Option 2: create an expression index matching the function used
CREATE INDEX idx_users_lower_email ON users (LOWER(email)); -- PostgreSQL syntax

SELECT *. Retrieving all columns when only a few are needed increases I/O, prevents covering-index optimizations, and can break application code silently if columns are added or reordered later. Naming only the needed columns is generally preferred.

SELECT customer_id, name, email FROM customers WHERE status = 'active'; -- preferred over SELECT *

N+1 patterns. Running one query to fetch a list, then one additional query per row to fetch related data, produces N+1 total queries instead of a single join or batched IN query. This is primarily an application-level anti-pattern (common with ORMs) rather than a raw SQL syntax issue, but it is worth recognizing.

-- N+1 pattern: one query per customer to fetch their orders, issued from application code in a loop
-- SELECT * FROM orders WHERE customer_id = 1;
-- SELECT * FROM orders WHERE customer_id = 2;
-- ... repeated N times

-- Fixed: a single query fetching all needed orders at once
SELECT * FROM orders WHERE customer_id IN (1, 2, 3, 4, 5);

When indexes hurt. Indexes are not free. Every additional index slows down INSERT, UPDATE, and DELETE, since each one must also be updated. Indexing a low-cardinality column (few distinct values, like a boolean flag) rarely helps, since the optimizer often finds a sequential scan cheaper than jumping through an index that doesn’t narrow the result much. Over-indexing a write-heavy table is a common performance mistake in the opposite direction from under-indexing a read-heavy one.

10. Functions, Gotchas, and Dialect Differences

10.1 String Functions Across Engines

String function names are one of the least standardized areas of SQL.

Operation PostgreSQL MySQL SQL Server SQLite
Concatenation \|\| or CONCAT() CONCAT() + or CONCAT() \|\|
Substring SUBSTRING(s, start, len) SUBSTRING(s, start, len) SUBSTRING(s, start, len) SUBSTR(s, start, len)
Trim whitespace TRIM(s) TRIM(s) TRIM(s) (2017+) TRIM(s)
Upper / lower case UPPER(s), LOWER(s) UPPER(s), LOWER(s) UPPER(s), LOWER(s) UPPER(s), LOWER(s)
Replace REPLACE(s, old, new) REPLACE(s, old, new) REPLACE(s, old, new) REPLACE(s, old, new)
String length LENGTH(s) or CHAR_LENGTH(s) LENGTH(s) (bytes) or CHAR_LENGTH(s) (chars) LEN(s) LENGTH(s) 
-- Concatenation, showing the split between the || operator and the CONCAT() function
SELECT first_name || ' ' || last_name FROM customers; -- PostgreSQL, SQLite
SELECT CONCAT(first_name, ' ', last_name) FROM customers; -- MySQL, portable everywhere
SELECT first_name + ' ' + last_name FROM customers; -- SQL Server, fails if any value is NULL

-- Substring
SELECT SUBSTRING(email, 1, 5) FROM customers; -- PostgreSQL, MySQL, SQL Server
SELECT SUBSTR(email, 1, 5) FROM customers; -- SQLite (also accepted in most other engines as an alias)

Note that LENGTH() in MySQL returns byte length, not character length, which differs for multi-byte (UTF-8) strings; CHAR_LENGTH() returns the character count.

10.2 Date and Time Functions Across Engines

Operation PostgreSQL MySQL SQL Server SQLite
Current date/time CURRENT_DATE, NOW() CURDATE(), NOW() GETDATE(), SYSDATETIME() DATE('now'), DATETIME('now')
Extract part EXTRACT(YEAR FROM d) YEAR(d), MONTH(d) DATEPART(year, d) strftime('%Y', d)
Add/subtract interval d + INTERVAL '1 day' DATE_ADD(d, INTERVAL 1 DAY) DATEADD(day, 1, d) DATE(d, '+1 day')
Difference between dates d2 - d1 DATEDIFF(d2, d1) DATEDIFF(day, d1, d2) JULIANDAY(d2) - JULIANDAY(d1)
Truncate to period DATE_TRUNC('month', d) DATE_FORMAT(d, '%Y-%m-01') DATETRUNC(month, d) (2022+) strftime('%Y-%m-01', d)
Format for display TO_CHAR(d, 'YYYY-MM-DD') DATE_FORMAT(d, '%Y-%m-%d') FORMAT(d, 'yyyy-MM-dd') strftime('%Y-%m-%d', d) 
-- Adding one month to today's date
SELECT CURRENT_DATE + INTERVAL '1 month'; -- PostgreSQL
SELECT DATE_ADD(CURDATE(), INTERVAL 1 MONTH); -- MySQL
SELECT DATEADD(month, 1, GETDATE()); -- SQL Server
SELECT DATE('now', '+1 month'); -- SQLite

-- Truncating a timestamp to the first of its month, useful for monthly grouping
SELECT DATE_TRUNC('month', order_date) AS month, SUM(total) FROM orders GROUP BY month; -- PostgreSQL
SELECT DATE_FORMAT(order_date, '%Y-%m-01') AS month, SUM(total) FROM orders GROUP BY month; -- MySQL

SQLite has no dedicated date/time storage type; dates are stored as text, real, or integer, and all date logic runs through its strftime/date/datetime functions.

10.3 Common Gotchas

Type casting. Implicit conversions between types can silently succeed with unexpected results, or fail depending on the engine. Explicit casting is safer.

SELECT CAST(price AS INTEGER) FROM products; -- ANSI standard, works everywhere
SELECT price::INTEGER FROM products; -- PostgreSQL shorthand
SELECT CONVERT(INT, price) FROM products; -- SQL Server alternative syntax

Integer division. Dividing two integers truncates the decimal portion in most engines rather than returning a fractional result, which is a frequent source of subtly wrong calculations.

SELECT 7 / 2; -- returns 3 in PostgreSQL, MySQL, SQL Server; integer division truncates
SELECT 7.0 / 2; -- returns 3.5, casting one operand to a decimal forces decimal division
SELECT 7 / 2.0 AS result; -- also 3.5, same fix

NULL in NOT IN. If a subquery or list used with NOT IN contains even one NULL, the entire condition evaluates to UNKNOWN for every row, silently returning zero rows. This is one of the most common and dangerous SQL bugs.

-- If any order has a NULL customer_id, this returns zero rows, even if matches clearly exist
SELECT * FROM customers WHERE customer_id NOT IN (SELECT customer_id FROM orders);

-- Fix 1: filter out NULLs explicitly in the subquery
SELECT * FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders WHERE customer_id IS NOT NULL);

-- Fix 2: use NOT EXISTS instead, which is unaffected by NULLs in the subquery
SELECT * FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

Empty string vs NULL. Most engines treat an empty string '' as a distinct value from NULL. Oracle is the notable exception: it treats an empty string as NULL for VARCHAR columns, which can break logic written for other engines.

SELECT * FROM customers WHERE middle_name = ''; -- matches rows with an empty string, not NULL, in most engines
SELECT * FROM customers WHERE middle_name IS NULL; -- a separate condition in most engines, but equivalent to the above in Oracle

Case sensitivity. String comparison case sensitivity depends on the engine’s default collation, not the SQL standard. PostgreSQL and SQL Server are typically case-sensitive by default for = comparisons (SQL Server depends on the database collation, often case-insensitive); MySQL is case-insensitive by default with the common utf8mb4_general_ci/_0900_ai_ci collations; SQLite is case-sensitive for = but case-insensitive for ASCII characters with LIKE.

SELECT 'Ana' = 'ana'; -- FALSE in PostgreSQL by default, TRUE in MySQL by default (collation-dependent)

Quoting identifiers. Unquoted identifiers are folded to a default case by the engine, and quoting preserves exact case while also allowing reserved words or special characters as names. Quote characters differ by engine.

Engine Quote character Default case folding for unquoted identifiers
PostgreSQL "double quotes" Lowercase
MySQL `backticks` Case-sensitive on Linux (filesystem-dependent), case-insensitive on Windows
SQL Server [square brackets] or "double quotes" Case-insensitive by default collation
SQLite "double quotes" or `backticks` Case-sensitive 
CREATE TABLE "Orders" (id INT); -- PostgreSQL: creates a table literally named "Orders", case preserved
SELECT * FROM Orders; -- fails: unquoted "Orders" folds to lowercase "orders", which does not exist
SELECT * FROM "Orders"; -- works: quotes preserve the exact case used at creation
